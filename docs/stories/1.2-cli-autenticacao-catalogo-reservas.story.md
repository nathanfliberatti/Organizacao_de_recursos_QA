## Story

**Como** Solicitante e Administrador,

**quero** autenticar-me e executar pelo CLI a consulta de recursos, a consulta de disponibilidade e a criação e listagem das minhas próprias reservas,

**para** usar o produto por uma interface funcional antes da construção de uma UI.

Esta é a primeira entrega CLI-first do produto e usa a API Spring como fonte de verdade. Nos fluxos de reservas de RF-04, este slice inclui somente consulta de disponibilidade, criação e listagem de reservas próprias; não inclui alteração nem cancelamento, que serão tratados em stories posteriores. A story também não inclui frontend, cadastro público nem acesso direto do CLI ao banco ou aos stores. A consulta de catálogo fica limitada aos campos de recurso existentes (`id` e `capacity`); filtros por tipo, localização, competência e demais atributos de RF-03 não estão definidos para os modelos atuais e não são considerados atendidos por esta entrega.

## Scope

### IN

- Autenticação de produto com usuários persistidos em PostgreSQL, senha BCrypt e JWT Bearer com validade máxima de 15 minutos.
- Provisionamento do primeiro `ADMINISTRADOR` exclusivamente por variáveis de ambiente explicitamente configuradas, sem credenciais padrão; criação posterior de usuários e atribuição de papéis por Administrador.
- Verificação do status ativo e dos papéis atuais do usuário em cada requisição autenticada, sem confiar em permissões desatualizadas dentro de um JWT ainda válido.
- API autenticada para listar recursos usando somente os atributos existentes, consultar disponibilidade, criar reservas e listar exclusivamente as reservas próprias; este slice não implementa alteração nem cancelamento de reservas.
- CLI Java 21 usando JDK `HttpClient`, sem acesso direto a stores ou ao PostgreSQL, com `RESOURCE_API_URL` configurável (padrão `http://localhost:8080`) e os comandos `resources list`, `resources availability`, `reservations create`, `reservations list` e `users create` (somente Administrador).
- O CLI será empacotado no JAR executável Maven existente e invocado como `java -jar target/organizacao-de-recursos-qa-0.1.0-SNAPSHOT.jar cli ...`; a versão do artefato deve acompanhar a versão declarada no `pom.xml`.
- Sintaxe mínima: `resources list --user <login>`; `resources availability --user <login> --resource-id <id> --starts-at <instante> --ends-at <instante> [--professor-id <id>]`; `reservations create --user <login> --resource-id <id> --starts-at <instante> --ends-at <instante>`; `reservations list --user <login>`; `users create --user <login-admin> --login <novo-login> --role <papel>`.
- Entrada de senha via `stdin`, autenticação a cada execução do CLI e token mantido apenas em memória durante a execução.
- Mensagens compreensíveis para intervalo inválido, falta de autenticação/permissão e conflito HTTP 409, sem exposição de detalhes internos.
- Documentação dos contratos e fluxos públicos implementados.

### OUT

- Qualquer frontend ou integração de UI com Spring; esses fluxos serão tratados em story posterior.
- Busca completa de RF-03 por tipo, capacidade, localização, competência e disponibilidade, além da definição de filtros/atributos por tipo de recurso. O catálogo desta story não satisfaz RF-03 integralmente.
- Novos atributos ou tipos de `Resource`, cadastro completo de salas/professores/materiais e expansão de regras de domínio além do necessário para estes comandos.
- Cadastro público, recuperação de senha, administração de usuários fora do comando `users create` ou autenticação de produto baseada no perfil `perf`.
- Aprovação de recursos restritos, manutenção, retirada/devolução, relatórios, notificações e outros comandos não listados no escopo.
- Alterar ou cancelar reservas (RF-04); esses fluxos serão detalhados e entregues em stories posteriores. Não incluir comandos CLI nem operações de API para alteração/cancelamento nesta story.
- Persistência local de credenciais, JWTs ou sessão do CLI.
- Qualquer UI; a escolha de framework/provedor JavaScript permanece em aberto.

## Acceptance Criteria

1. **Dado** um PostgreSQL sem usuário `ADMINISTRADOR`, **quando** a aplicação for inicializada com `BOOTSTRAP_ADMIN_LOGIN` e `BOOTSTRAP_ADMIN_PASSWORD` explicitamente configuradas, **então** deve provisionar um único usuário Administrador com senha armazenada em BCrypt; reinicializações não devem recriar nem redefinir a senha desse usuário. **E** se o bootstrap for necessário e qualquer variável estiver ausente ou vazia, a aplicação deve falhar de forma explícita e segura, sem credenciais padrão. Nenhuma rota pública deve permitir criar o primeiro Administrador.
2. **Dado** um Administrador autenticado, **quando** executar `users create --user <login-admin> --login <novo-login> --role <papel>` e fornecer por `stdin` primeiro a senha do Administrador e depois a senha inicial do novo usuário, **então** o usuário ativo deve ser persistido e conseguir autenticar-se com um dos papéis `SOLICITANTE`, `RESPONSAVEL` ou `ADMINISTRADOR`; usuários sem papel Administrador não podem criar usuários. O endpoint `POST /api/users` deve exigir autorização no servidor, independentemente do CLI.
3. **Dado** um usuário ativo com credenciais válidas, **quando** enviar `POST /api/auth/login`, **então** a API deve retornar um JWT Bearer cuja validade não exceda 15 minutos. Credenciais inválidas ou usuário inativo não autenticam. Senhas e tokens não podem aparecer em logs, mensagens de erro ou saída normal do CLI.
4. **Dado** um JWT ainda válido, **quando** o usuário for desativado ou tiver seus papéis alterados no banco, **então** as requisições seguintes devem negar o usuário inativo ou aplicar imediatamente os papéis atuais, sem preservar acesso concedido por claims antigas. Uma chamada anônima a rota protegida retorna 401; uma chamada autenticada sem o papel exigido retorna 403.
5. **Dado** recursos persistidos, **quando** um usuário autenticado executar `resources list`, **então** o CLI deve obter `GET /api/resources` e apresentar somente identificador e capacidade dos recursos existentes. Esta consulta não oferece filtros por tipo, capacidade, localização ou competência e não deve ser apresentada como conclusão de RF-03.
6. **Dado** um recurso e um intervalo válido, **quando** o usuário executar `resources availability --user <login> --resource-id <id> --starts-at <instante> --ends-at <instante> [--professor-id <id>]`, **então** o CLI deve consultar a API e apresentar o resultado de disponibilidade. **Quando** o término for igual ou anterior ao início, a API deve rejeitar o intervalo com erro 4xx compreensível e o CLI deve indicar a correção necessária sem exibir stack trace ou detalhes internos.
7. **Dado** um Solicitante autenticado, **quando** executar `reservations create --user <login> --resource-id <id> --starts-at <instante> --ends-at <instante>`, **então** a API deve derivar `requesterId` e `professorId` do subject canônico autenticado (login), conforme ADR-002, e persistir a reserva usando o contrato existente de `resourceId`, `startsAt`, `endsAt` e `professorId`. A criação não aceita `--professor-id` nem identidade alternativa no payload. Um teste de integração deve enviar diretamente à API um `professorId` alternativo e verificar que a requisição é rejeitada com 4xx e nenhuma reserva é criada para a agenda alheia; o teste caixa-preta também deve confirmar que o CLI não permite selecionar outro professor na criação. `resources availability` pode continuar aceitando `--professor-id` opcional como consulta. Intervalo com término igual ou anterior ao início deve ser rejeitado conforme RF-13. Uma reserva conflitante deve retornar HTTP 409 com mensagem compreensível no CLI; um teste concorrente contra PostgreSQL real deve verificar que, sob solicitações incompatíveis simultâneas, no máximo uma reserva é confirmada, conforme RF-05/RF-06.
8. **Dado** um usuário autenticado com reservas próprias e reservas pertencentes a terceiros, **quando** executar `reservations list`, **então** o CLI deve obter `GET /api/reservations` e listar exclusivamente as reservas cujo solicitante persistido corresponde à identidade autenticada. O filtro deve ser imposto pela API, inclusive para Administrador, e não somente pelo CLI. Este slice inclui apenas disponibilidade, criação e listagem de reservas próprias; alteração e cancelamento de RF-04 ficam para stories posteriores e não devem ser implementados nesta story.
9. **Dado** qualquer comando de produto, **quando** ele for executado, **então** o CLI deve solicitar a senha por `stdin`, autenticar-se novamente para aquela execução e enviar as chamadas à API usando JDK `HttpClient`. O JWT pode existir apenas em memória durante o processo: não deve ser gravado em arquivo, configuração, cache ou histórico; o segredo não deve ser passado como argumento de processo.
10. **Dado** a implementação dos fluxos acima, **quando** forem executados os testes, **então** testes de integração devem exercitar a API Spring real contra PostgreSQL com Testcontainers e cobrir bootstrap, hash de senha, login, papéis atuais, posse, rejeição de `professorId` alternativo e conflitos, incluindo uma verificação concorrente real de reservas incompatíveis. Testes caixa-preta do CLI usando `ProcessBuilder` devem executar o JAR reempacotado real após a fase `package`, fornecer a senha por `stdin` e validar os comandos e mensagens observáveis, sem mocks de transporte entre CLI e API. `./mvnw -B verify` deve passar.
11. **Dado** que a autenticação de produto está habilitada fora do profile `perf`, **quando** a aplicação iniciar sem `RECURSOS_JWT_SECRET`, com valor vazio ou com menos de 32 bytes, **então** a inicialização deve falhar antes que rotas protegidas sejam disponibilizadas; não pode existir default ou fallback. Um teste de inicialização deve cobrir separadamente os três valores inválidos. Com 32 bytes ou mais a configuração pode prosseguir. O profile `perf` deve iniciar sua configuração de autenticação independentemente de `RECURSOS_JWT_SECRET`, usando sua própria configuração e sem fallback para autenticação de produto.

- Decisões de arquitetura confirmadas pelo solicitante e validadas pelo @architect para este slice: monólito Spring Boot, API como fonte de verdade, autenticação JWT de produto e CLI Java como cliente HTTP. O perfil `perf` não é autenticação do produto.

## Risks

- Claims de papel no JWT podem manter privilégios após uma mudança; cada requisição deve consultar status e papéis atuais no PostgreSQL.
- Bootstrap sem defaults precisa falhar fechado quando ainda não existe Administrador; logs de startup não podem revelar a senha configurada.
- A rota de listagem de reservas pode expor dados de terceiros se a posse for aplicada apenas no cliente ou se uma consulta administrativa ignorar o filtro obrigatório.
- O modelo atual de `Resource` não contém os atributos necessários à pesquisa completa de RF-03; qualquer filtro além dos campos existentes expandiria indevidamente o escopo.
- Testes Testcontainers e CLI subprocesso podem depender de Docker e configuração de ambiente; falhas ambientais devem ser diferenciadas de falhas de comportamento.
